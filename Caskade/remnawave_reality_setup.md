# Руководство по настройке VLESS Reality в Remnawave

Данное руководство содержит полное описание архитектуры, правил маршрутизации, конфигурации базы данных и диагностических процедур для связки Remnawave + VLESS Reality. Оно поможет быстро развернуть или восстановить работу нод без лишних трудностей.

---

## 1. Архитектура и суть проблемы

VLESS Reality маскирует VPN-трафик под обычные безопасные TLS-соединения (HTTPS). 
Ключевой момент работы Reality — это **Destination (`dest`)** и **Server Names (`serverNames` / `sni`)**. 

Существует два основных сценария работы, которые категорически нельзя смешивать:

### Сценарий А. Маскировка под внешний доверенный сайт (например, Google/Microsoft)
*   **Используется, когда:** на сервере ноды **нет собственного веб-сайта с валидным SSL/TLS-сертификатом**.
*   **Принцип:** Клиент подключается к ноде с подмененным SNI доверенного внешнего сервера, а нода пересылает TLS Client Hello на этот внешний сервер.
*   **Настройки:**
    *   `dest`: `google.com:443` (или любой другой крупный сайт с поддержкой TLSv1.3/HTTP2).
    *   `serverNames` / `sni`: `["google.com", "www.google.com"]` (домен в подписке и профиле должен в точности совпадать с сервером назначения!).
*   **Важное ограничение:** В `serverNames` **нельзя** указывать свой домен (например, `alphaceiling23.ru`), если `dest` указывает на чужой сервер (например, `google.com:443`). В логах это приведет к ошибкам:
    `server name mismatch: alphaceiling23.ru` или `TLS handshake error`.

### Сценарий Б. Локальный веб-сервер маскировки (свой домен) — Рекомендуемый
*   **Используется, когда:** на сервере ноды **запущен локальный веб-сервер (Nginx/Caddy)**, обслуживающий ваш собственный домен по безопасному порту (например, `8443`).
*   **Принцип:** Клиент использует ваш реальный домен (`alphaceiling23.ru`) в качестве SNI. Нода перенаправляет трафик локальному веб-серверу на порту `8443`, который отдаёт настоящий TLS-сертификат для этого домена.
*   **Настройки:**
    *   `dest`: `127.0.0.1:8443` (нода пересылает запросы на локальный порт Nginx).
    *   `serverNames` / `sni`: `["alphaceiling23.ru"]`.
*   **Важное требование:** На сервере ноды обязательно должен быть запущен веб-сервер, который слушает порт `8443`.
    *   Если веб-сервер **выключен** или не слушает порт `8443` (как было при развёртывании на Yandex Cloud), Xray выдаст ошибку `connection refused` и **не запустится**.

## 2. Структура Базы Данных Remnawave

Панель Remnawave хранит все конфигурации нод в СУБД PostgreSQL. Чтобы изменить параметры подключения или маскировки, необходимо обновить 4 таблицы:

1.  **`nodes`** — содержит физический IP-адрес/домен ноды, по которому панель управляет ею по API.
2.  **`hosts`** — определяет адрес и SNI, которые генерируются в ссылках подписки клиентов (поле `address` и `sni`).
3.  **`config_profile_inbounds`** — хранит активный JSON-конфиг для входящих подключений (inbounds) конкретной ноды.
4.  **`config_profiles`** — шаблон конфигурации, который подтягивается при создании новых пользователей или обновлении профилей.

## 3. Скрипт миграции и восстановления конфигурации

Для быстрого переноса ноды на новый сервер или исправления конфигурации используется SQL-скрипт. Ниже приведён пример SQL-запроса для переезда ноды `RU3` на новый IP-адрес Aeza с использованием Сценария Б (Nginx маскировка на порту `8443` для домена `alphaceiling23.ru`):

```sql
-- 1. Обновление IP-адреса управления нодой в панели
UPDATE nodes SET address = '109.107.189.149' WHERE name = 'RU3';

-- 2. Обновление IP и домена (SNI) в ссылках подписки
UPDATE hosts
SET address = '109.107.189.149', sni = 'alphaceiling23.ru'
WHERE remark = 'RU-Reality';

-- 3. Восстановление локального веб-сервера и домена в активном профиле входящих подключений
UPDATE config_profile_inbounds
SET raw_inbound = jsonb_set(
    jsonb_set(raw_inbound,
        '{streamSettings,realitySettings,dest}',
        '"127.0.0.1:8443"'
    ),
    '{streamSettings,realitySettings,serverNames}',
    '["alphaceiling23.ru"]'
)
WHERE profile_uuid = '055045f9-a3cf-467e-84a2-55ccbf25cfa1';

-- 4. Обновление шаблона профиля конфигурации (для генерации новых конфигов)
UPDATE config_profiles
SET config = jsonb_set(
    config,
    '{inbounds}',
    (
        SELECT jsonb_agg(
            CASE
                WHEN elem->>'tag' = 'VLESS_Reality_RU'
                THEN jsonb_set(
                    jsonb_set(elem,
                        '{streamSettings,realitySettings,dest}',
                        '"127.0.0.1:8443"'
                    ),
                    '{streamSettings,realitySettings,serverNames}',
                    '["alphaceiling23.ru"]'
                )
                ELSE elem
            END
        )
        FROM jsonb_array_elements(config->'inbounds') elem
    )
)
WHERE uuid = '055045f9-a3cf-467e-84a2-55ccbf25cfa1';
```

### Автоматизация через Python
Этот SQL можно применить удаленно с машины разработчика одной командой с помощью Python-скрипта (см. файл [migrate_to_aeza.py](file:///d:/Gravity/Caskade/scratch/migrate_to_aeza.py)):


## 4. Перезапуск и проверка статуса сервисов

После любого изменения конфигурации в БД обязательно нужно перезапустить и панель, и саму ноду, чтобы применились новые параметры:

### Шаг 1. Перезапуск панели (на основном сервере, например, SWE)
Выполните по SSH на панели управления:
```bash
cd /opt/remnawave
docker compose restart remnawave
```

### Шаг 2. Перезапуск ноды (на целевом сервере, например, RU)
Выполните по SSH на сервере ноды:
```bash
docker restart remnanode
```

## 5. Диагностика и Логи

Если клиенты не могут подключиться или нода отображается как неактивная, выполните следующие шаги:

### 1. Проверка портов на сервере ноды
Убедитесь, что веб-сервер действительно слушает порт `8443`, а нода слушает `443` (для Reality):
```bash
ss -tlnp | grep -E "443|8443"
```
*   Если порт `8443` свободен — Nginx выключен. Reality с `dest: 127.0.0.1:8443` не запустится.
*   If port `443` is not listened to — xray inside the `remnanode` container has crashed.

### 2. Чтение логов Xray на ноде
Это самый точный способ понять, в чём проблема:
```bash
docker exec remnanode tail -n 50 /var/log/supervisor/xray.out.log
```

#### Типичные ошибки в логах:
*   **`dial tcp 127.0.0.1:8443: connect: connection refused`**
    *   *Причина:* Вы выбрали Сценарий Б (собственный домен), но локальный Nginx на ноде не запущен или настроен на другой порт.
    *   *Решение:* Запустите Nginx или временно переключите `dest` на `google.com:443`, а `serverNames` на `["google.com"]` (Сценарий А).
*   **`server name mismatch: ...`**
    *   *Причина:* В `serverNames` указан домен, который не соответствует домену, обслуживаемому сервером `dest`.
    *   *Решение:* Приведите `serverNames` и `dest` в соответствие друг другу по правилам Сценариев А или Б.
*   **`failed to read config`**
    *   *Причина:* Панель отдала невалидный JSON-конфиг или нода не может достучаться до API панели.
    *   *Решение:* Проверьте статус панели, сетевую связность и валидность записей в таблице `config_profile_inbounds`.
